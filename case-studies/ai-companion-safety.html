Case studyConsumer · Child safety · AIShipped product

Telling a parent what’s happening — without reading a word.

Teenagers now spend hours inside AI companion apps, and parents have no idea whether that is twenty minutes or four hours a night. The obvious product is a surveillance tool. The constraint I set was that the system must never be able to read a single message — and that this be enforced by architecture, not promised in a privacy policy.

The challenge.

AI companion apps — character chat, synthetic partners, roleplay — are a genuinely new category of teenage screen time, and unlike social media they are conversational, private and emotionally sticky. The parents who worry about it want one question answered: how much, and is it getting worse?

Every existing answer to that question is a monitoring product that reads the conversations. That trade is bad on three counts: it is the most invasive possible reading of a private exchange, it destroys the trust between parent and teenager that makes any intervention work, and it creates a store of intimate minor-related content that is a liability the moment it exists.

So the design question was not “how do we monitor safely”. It was: how much can you learn from the shape of usage alone, and can you make reading impossible rather than merely disallowed?

The constraints.

Never readableNo message content, ever — enforced structurally
Minor's dataSmallest viable data set; nothing retained that isn't used
The subject has agencyThe teenager is a participant, not a target
Multi-surfaceiOS, browser and web must agree on one model
Solo buildNo team — complexity is the binding constraint

The approach.

Signal, not content. The system collects one thing: which category of platform was in use, for how long, on which day. Not who was talked to, not what was said, not even the specific conversation. On the browser side that meant the extension reads the active tab’s hostname and nothing else, maps it to a platform category, and discards the rest. The extension requests no host permissions on any monitored site — it holds permission for its own backend and nothing more. It is not that it chooses not to read pages; it cannot, and any reviewer can verify that from the manifest in ten seconds.

On-device aggregation, by borrowing someone else’s sandbox. On iOS the usage data comes from Apple’s device-activity framework, which runs the reporting extension in a sandbox with no network access. That is normally described as a limitation. Here it was the whole point: exact session boundaries are structurally unavailable to the app and therefore to the backend, and what leaves the device is a threshold crossing — a child identifier, a minute count, a timestamp. The privacy property is enforced by the operating system, not by my code behaving well.

Deliberately coarse granularity. Everything rolls up to (child, day, platform category). That is the finest resolution the system can hold, which makes a whole class of future feature requests — “can we see the actual chats” — not a policy conversation but a rebuild. Constraints only survive when violating them is expensive.

A credential for the person being monitored. The teenager gets their own sign-in — a family code and PIN, distinct from the parent’s account — so they can see exactly what their parent sees, and attach their own notes to a day. This is the piece most parental-control products skip, and it is the difference between a tool a family uses together and one a teenager routes around within a week.

No RLS-bypassing key, anywhere. The child credential could have been implemented quickly using the database’s admin API, which would have meant introducing a service-role key that bypasses row-level security. I built it instead with SECURITY DEFINER functions with a pinned search path, so the codebase never holds a credential that can read every family’s data. The shortcut would have saved a day and permanently changed the security posture of the system.

The honest caveat, written into the migration at the time: a code-and-PIN pair is not cryptographic proof of identity. It is the same trust model as a share link. It gives the child a real, separate credential; it does not pretend to be more than that. Rate limiting — eight wrong attempts locks that code for fifteen minutes, shared across every function that accepts it — is what makes it survivable rather than the credential itself.

Outcomes.

Zero message content Not stored, not transmitted, not accessible. The strongest privacy claim a monitoring product can make, and it is verifiable from the extension manifest and Apple's sandbox rather than taken on trust.
Three surfaces, one model iOS system extension, browser extension and web dashboard converge on the same (child, day, platform) rollup, with timezone handled per family so a "day" means the family's day.
Shipped, with billing Not a prototype: subscriptions, thresholds and alerting, weekly digests, and a dashboard a non-technical parent can read in thirty seconds.

Three lessons that travelled.

1 · The best privacy control is one you cannot revoke. “We don’t read messages” is a promise; “we hold no permission that would let us” is a property. Where a platform sandbox already enforces the boundary you want, adopting that constraint is worth more than any amount of policy documentation — and it survives changes of ownership, pressure from a feature request, and your own future bad judgement. This is the same argument as policy-as-code, and it lands the same way.

2 · Design the data model around the answer, not the data available. Far more was technically collectable than was collected. Starting from the single question a parent actually has — how much, and is it trending — produced a schema whose finest grain is a day. Starting from what the APIs could provide would have produced session-level data, an obligation to secure it, and a product nobody would let their teenager install.

3 · When the subject of a system has no standing, the system gets routed around. Giving the monitored teenager their own login and the ability to annotate their own days changed the product from surveillance to a shared instrument. It is the same lesson as an architecture review board that engineers avoid, or a platform nobody adopts: a control that the person on the receiving end has no voice in is a control with a short life.

Why this one is here. Most of my case studies are large regulated programmes with teams around them. This one was built solo, end to end — architecture, Swift, TypeScript, schema, billing, App Store submission. It is on this site because the interesting part is not the scale but the constraint: it is the clearest example I have of making the safe thing structurally enforced rather than procedurally promised, which is the argument the rest of this site makes about regulated systems, tested somewhere the stakes are personal.
